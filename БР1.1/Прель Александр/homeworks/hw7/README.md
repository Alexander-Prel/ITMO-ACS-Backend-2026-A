# ДЗ7. Облачная инфраструктура бронирования столиков

## Архитектура

Учебная ВМ обслуживает ручное развёртывание ЛР4 и автоматизацию ДЗ6. Облачная версия ЛР7 использует отдельный управляемый Kubernetes с Linux-узлами amd64. Два окружения могут работать независимо. Адреса ВМ, облачный аккаунт и лимит расходов назначает владелец учебного стенда.

| Ресурс | Выбранное решение | Причина |
| --- | --- | --- |
| Сеть | VPC, публичный балансировщик, приватная подсеть узлов с исходящим доступом к реестру | Единственный внешний API — Gateway. Базы и брокер остаются внутри. |
| Узлы | Проектный минимум: 2 worker по 2 vCPU / 4 GiB; кластер и мониторинг измерять до выбора окончательного размера | Две реплики Gateway могут размещаться на разных узлах. Нужен запас для системных подов и наблюдаемости. |
| Маршрутизация | Балансировщик → Gateway → Accounts, Catalog, Bookings, Notifications | Внутренний HTTP использует имена Service. Внешний доступ ограничить адресами клиента защиты и генератора нагрузки в правилах облачной сети. |
| Данные | По RWO-диску 1 GiB на сервис с SQLite, 2 GiB для RabbitMQ. Облачный CSI и default StorageClass | Стабильная идентичность StatefulSet и отдельный диск сохраняют данные при пересоздании пода. |
| Сообщения | Bookings пишет события в outbox; RabbitMQ доставляет их в Notifications | Остановка получателя не отменяет бронь. При восстановлении проверяется доставка событий и отсутствие дублей. |
| Образы и доступ | Пять образов GHCR по digest. Отдельные секреты приложения и отдельная учётная запись деплоя с правами в booking-sem2 | Откат указывает на конкретный набор образов. Доступ к реестру выдаётся только на чтение со стороны кластера. |
| Наблюдаемость | ВМ: Prometheus, node-exporter, blackbox, Loki, Promtail, Grafana. Кластер: Metrics Server для HPA, Prometheus и Grafana для испытаний | Оценивать доступность сервисов, CPU Gateway, реакцию HPA, реальные p95/p99 и ошибки. |

## Сохранность и отказоустойчивость

Gateway не хранит сессии и базы. Начальный диапазон HPA — 2–4 реплики, порог CPU — 60% от запроса 100m. Readiness исключает неготовые конечные точки из балансировки. Для обслуживания узлов предусмотрен PodDisruptionBudget и предпочтение разных узлов. Восстановление сервиса с диском занимает время повторного присоединения тома. Одна реплика RabbitMQ и зональный диск остаются точками временной недоступности. Репликация SQLite между независимыми подами в эту архитектуру не входит.

Для восстановления после потери диска нужен согласованный снимок: остановить записи, дождаться отправки outbox, зафиксировать четыре БД и состояние брокера, возобновить работу. Проверять восстановление в отдельном namespace по наличию ранее созданной брони и уведомления. Учебные цели RPO до суток и RTO до часа относятся к проекту; фактические значения определяет учебное восстановление. Для нескольких зон потребуется переход на внешний отказоустойчивый сервер БД и кластер брокера.

## Критерии проверки проекта

1. HPA указывает на Gateway. Все процессы записи в SQLite имеют единственного владельца PVC.
2. Извне доступен только Gateway. Перед испытаниями проверяются StorageClass, attach/detach дисков, Metrics API и работа балансировщика.
3. Архив сборки содержит Git SHA и пять digest. Проверка /ready подтверждает доступность четырёх внутренних сервисов, сквозной сценарий создаёт и отменяет бронь.
4. Гипотеза нагрузки: при росте запросов увеличится число Gateway; узкое место может находиться в Catalog или Bookings. Решение о тюнинге принимается по сопоставлению графиков и результатов двух одинаковых прогонов.

Исходные условия взяты из [README курса](https://github.com/kantegory/ITMO-ACS-Backend-2026-A/blob/cf6ff89837eab1aefba01a59862af6a39dd0a603/README.md). Предложенные размеры и показатели — проектные. Управляемый кластер, балансировщик и диски требуют отдельной учебной квоты или согласованного бюджета.
